Architecture notes

How Liam is built.

Liam's source is private. This page isn't — it's a real account of the design, written the way I'd document it for someone else to maintain, not as a pitch. Where the code and a tidier description would disagree, this follows the code.

Last reviewed October 2026 · Referenced from the portfolio

01 What Liam is

Liam is an assistant built for one person's work: running the day-to-day of an independent publishing and marketing operation — manuscript editing, continuity checking, brainstorming, drafting, and social content — plus voice interaction while writing or recording, where typing isn't practical. It isn't a product. There's one user, one canon of reference material it knows, and one set of credentials that can reach it. It's reachable from a desktop app, a phone, and a messaging bot, all backed by the same running process rather than three separate builds.

02 Why hybrid

The starting constraint: no model that runs entirely on a laptop, with no network connection, matches a frontier cloud model for the heaviest reasoning. But routing everything to the cloud gives up three things that matter for this specific use — the ability to keep working with no internet, keeping manuscript content off a network call by default, and not paying cloud-model latency for a routine request that a local model can answer just as well.

So the system doesn't pick one. A router sits between the interface and the models and decides, per request, where a message actually goes: a locally hosted model for private, offline-fine, or quick work; a frontier model when the request is heavy enough — real structural editing, developmental feedback, anything where the reasoning gap still matters — to justify the round trip. The router is the one piece of this that makes the hybrid idea real rather than aspirational; everything else is built to make its decision cheap to act on, by keeping memory and document state available to whichever backend actually answers.

The same idea extends one level up, not just between models but between machines: a second always-on machine is designed to take on heavier or longer-running work when it's reachable, registering itself and being handed tasks the same way a model is chosen — see what this is not for where that stands today.

03 Architecture

One backend process serves every interface. The desktop app, the phone page, and the messaging bot all call the same API surface rather than each having their own routing, memory, or document logic — a fix applied once reaches all three at once, and a bug fixed in one place can't still be live in another.

Everything downstream of the backend — routing, memory, documents, voice — is shared; nothing downstream knows or cares which interface a request came in through.

Each piece is meant to be replaceable without the others caring: the router doesn't know which interface sent a request, the models don't know how memory was assembled, and the voice daemon talks to the backend through the same API surface the browser uses rather than a special internal path. That's less an elegance preference than a practical one — the voice daemon in particular has to run in its own OS process (more on why in Voice), so a shared API was the only option that didn't mean duplicating the routing and memory logic a second time.

04 Memory and canon

Two things, paired. A vector store indexes manuscript content so it can be retrieved by meaning, not just by filename. Alongside it, a shared structured reference — plain text, not a database — holds the material that has to stay consistent no matter which model answers: character and world detail, terminology, house style, the kind of thing a human editor would call a style guide. Every model in the system, local or cloud, reads from the same reference before answering, rather than each one building its own independent sense of what's correct.

The reason this got built at all: a hybrid system answers the same kind of question from different backends on different turns, sometimes within the same conversation. Without a shared source of truth, that's a direct path to the system contradicting itself — a detail stated one way by the local model and a different way by a cloud model an hour later, with no way to tell which one is authoritative. The reference exists so that question doesn't come up.

05 Documents: sync and editing

Working documents live in cloud storage and mirror into a local cache. Reads come from the cache — no live network call sits in the conversation loop — and the local copy and its cloud counterpart are treated as two synced copies of the same document, neither one authoritative over the other. An edit made through one propagates to the other; the system doesn't assume the local copy should simply replace the cloud one, or the reverse.

How an edit actually applies

A dictated edit never rewrites a whole file. It applies as a targeted, in-place replacement of the specific passage named — through a direct document-editing API when the file format supports it, or by editing the local cached copy and pushing the identical change back when it doesn't (a plain word-processor file, for instance, where that API simply can't open the format at all). Both paths land on the same outcome: one passage changed, everything else untouched.

When it refuses

If the requested passage isn't found, if it matches in more than one place, or if the cloud copy has changed since the last sync, the system reports that and changes nothing. No best-effort guess, no silent overwrite. That refusal is the actual point of this whole path — the alternative is a system that sometimes edits the wrong sentence and never tells you.

06 Voice

The wake word is a custom-trained model on the assistant's own name, not a stock keyword — trained once, offline, against a purpose-built dataset rather than reused from a general voice-assistant library. It runs in a separate OS process from the rest of the system, because it has to listen continuously, system-wide, regardless of which window or app currently has focus; that's not something a browser tab or a single in-app component can do on its own.

Speech in and speech out both run on local, offline engines — dictation and spoken replies don't depend on a network connection even when the request itself gets routed to a cloud model. Replies are interruptible at sentence boundaries, so a long passage being read aloud can be stopped and redirected mid-stream instead of having to finish.

One deliberate behavioral limit, not an oversight: the system doesn't listen for a new wake word while it's actively speaking. With no acoustic echo cancellation in this setup, the assistant's own voice can leak back into the microphone at close to full confidence — a real, measured false trigger during testing, not a hypothetical one. Listening resumes in the gaps between spoken segments instead, which is close to but not identical to true mid-sentence interruption.

07 Boundaries

By default, nothing leaves the machine: raw audio, the local model's reasoning, and cached document content all stay local unless the router decides a specific request is worth sending onward. What does leave, when it does, is the text of that request and whatever context it needs — sent to a model provider's API over an encrypted connection, nothing more.

The language layer — whatever model is answering a given request — is kept separate from anything that can actually change a file. A model doesn't get general file-system or shell access; the only write path is the narrow, specific one described above, with its own refusal rules, not a general-purpose tool a model could point anywhere. Remote reach works the same way: the system is reachable off the local network only over a private, authenticated connection (a mesh VPN, not a port opened to the public internet), every request carries a credential, and repeated failed attempts from the same source get temporarily locked out rather than allowed to keep guessing.

08 Testing

The automated suite is deliberately narrow: it covers the specific paths that have actually broken in real use — document and filename matching, authentication, reading-session state — as a guard against regressing those particular incidents, not as a general coverage target. That's a real trade-off, made on purpose, for a single-user tool where the cost of a gap is personal inconvenience, not a production outage.

The voice layer has no automated coverage at all. It depends on a separate runtime environment that the main test setup can't even import, which is a real gap, not a stylistic choice — every fix to the wake-word or speech pipeline has been verified by actually using it and reading the logs afterward, not by a test suite catching a regression before it shipped.

09 What this is not

Said plainly, not softened:

  • Built for one person. Single authorized user, one person's reference material, one set of credentials. Nothing about the design assumes more than one person will ever use it.
  • Phase one of a larger plan. A second always-on machine is meant to eventually handle home-automation work entirely separate from this assistant, registering with this system and taking over heavier tasks when reachable. The handoff logic between the two is built and its control flow is verified — registration, task handoff, fallback on failure — but it has never run end to end with both machines actually running live models at the same time. The home-automation half hasn't been started at all.
  • No voice testing. Covered above, repeated here because it belongs in this list too: the voice pipeline's correctness depends entirely on manual verification, not an automated safety net.
  • No native mobile app. Phone access is a web app added to the home screen, not something installed from an app store — a deliberate choice to avoid a second codebase and a store-review process, not a missing feature.
  • One machine, no redundancy. Everything runs on a single laptop. If it's off, asleep, or disconnected, nothing is reachable remotely — there's no failover and none is planned while this stays a single-user tool.
  • The marketing-content pipeline is still a plan, not a running system. Generating a finished social post from a manuscript passage, end to end, is designed but not built; what exists today is the routing and memory underneath it.
